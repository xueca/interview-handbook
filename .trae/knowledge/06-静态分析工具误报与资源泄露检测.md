## 问题 1：正则扫描全文件内容导致字符串误报

### 问题根因

`apiImportsBusiness` 直接用正则扫描整个文件内容来判断 import 路径：

```js
// ❌ 旧代码：字符串字面量中的 composables/ 也会触发
function apiImportsBusiness(content) {
  return /(?:require\(|from\s+)['"][^'"]*(?:composables|stores)\//.test(content);
}
```

如果文件里有 `const tip = '请从 composables/useX 导入'` 这样的字符串字面量，会被误判为"API 层依赖了业务层"。

**本质原因**：正则不分上下文，把注释/字符串中的路径也当成了真实的 import 语句。静态分析工具最常见的误报来源之一。

### 解决方案

先提取所有 import/require 语句，再在提取出的路径列表中匹配：

```js
function extractImportStatements(content) {
  const statements = [];
  const importRegex = /import\b[\s\S]*?\bfrom\s+['"]([^'"]+)['"]|import\s+['"]([^'"]+)['"]/g;
  const requireRegex = /require\s*\(\s*['"]([^'"]+)['"]\s*\)/g;

  let match;
  while ((match = importRegex.exec(content)) !== null) {
    statements.push(match[1] || match[2]);
  }
  while ((match = requireRegex.exec(content)) !== null) {
    statements.push(match[1]);
  }
  return statements;
}

function importsContain(imports, prefixes) {
  return imports.some(src => prefixes.some(prefix => src.includes(prefix)));
}
```

所有 import 依赖检查函数改为接收 `imports` 数组而非原始 content。`.vue` 中检查 axios/sse.js 也改用同一机制。

### 如何避免再次发生

- **静态分析的正则一定要作用在精确的 AST 节点上**，而不是整个文件内容
- 对于 import 检查，先提取 import 语句再匹配，永远不要用正则扫描全文
- 代码审查时留意：正则搜索范围是否过于宽泛（有没有 `.test(content)` 对全文而非特定语句）
- 可以进一步用 `@babel/parser` 解析 AST 来做 import 检测，完全杜绝字符串/注释误报

## 问题 2：资源泄露检测过于宽松

### 问题根因

旧代码只检查"文件中是否出现了清理函数"：

```js
// ❌ 旧代码：只要文件里有任意清理函数，就不报泄露
const cleanupPattern = /onUnmounted|clearInterval|clearTimeout|controller\.abort|\.close\(\)/;
const hasCleanup = cleanupPattern.test(content);
if (!hasCleanup) issues.push('可能存在资源泄露');
```

**问题**：
- `setInterval` 和 `clearTimeout` 配对也能通过检查（不同资源类型交叉匹配）
- 创建了 3 个 `setInterval` 但只写了 1 个 `clearInterval` 也不会报
- 检查粒度是"文件级"而非"资源类型级"

### 解决方案

按资源类型分别统计创建与清理的调用次数，只有创建数 > 清理数时才报：

```js
function detectResourceLeaks(content) {
  const pairs = [
    { create: /\bsetInterval\s*\(/g,      cleanup: /\bclearInterval\s*\(/g,  name: 'setInterval' },
    { create: /\bsetTimeout\s*\(/g,        cleanup: /\bclearTimeout\s*\(/g,  name: 'setTimeout' },
    { create: /new\s+AbortController\s*\(/g, cleanup: /\.abort\s*\(/g,       name: 'AbortController' },
    { create: /new\s+EventSource\s*\(/g,   cleanup: /\.close\s*\(\)/g,       name: 'EventSource' }
  ];
  // ... 每种类型单独统计，创建数 > 清理数时才报告
}
```

### 如何避免再次发生

- 资源泄露检测必须按类型配对，不能笼统地"文件里有清理函数就行"
- 四种常见资源需要独立对待：`setInterval`、`setTimeout`、`AbortController`、`EventSource`
- 更严格的做法：追踪变量绑定，确保同一个 `setInterval` 返回值确实传入了 `clearInterval`
- composables 中应使用 `onUnmounted` hook 统一清理，避免零散清理导致遗漏

## 问题 3：重复代码块检测阈值过低

### 问题根因

`duplicate_code_detector.js` 用 4 行哈希块检测重复，对 `const x = ref(0)` 这样的连续声明模式会频繁误报：

```js
// 这些 4 行连续 ref 定义会被误判为重复
const a = ref(0);
const b = ref(0);
const c = ref(0);
const d = ref(0);
```

**本质原因**：4 行作为哈希块太短，Vue/React 项目中常见的声明式代码很容易恰好形成 4 行相似结构。

### 解决方案

- 块大小从 4 行提升到 6 行：显著降低常见声明模式的误报
- 添加 `severity: 'warning'`：即使触发也只告警不阻断

### 如何避免再次发生

- 重复代码检测的块大小取决于项目代码风格——Vue reactivity 声明密集的项目至少用 6 行
- 重复代码发现应该设置 `warning` 级别，因为不一定是真正的重复，需要人工审查
- 对于 `isMeaningfulLine` 过滤后的块，6 行实际对应大约 6-10 行原始代码，足够判断是否为有意识重复

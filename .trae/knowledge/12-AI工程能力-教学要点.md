## 模块10：Code Guardian MCP Server (⭐⭐⭐⭐⭐)

### ① 功能定位
MCP Server，让 AI 在修改代码前后自动检查文件大小、ESLint、架构合规等6项指标。

### ② 设计思路

**为什么用 MCP 而不让 AI 直接调 REST API？**
- AI 需自动发现工具（MCP 的 ListTools），REST API 需人工告知 endpoint
- MCP 结构化输入输出（JSON Schema），REST API 返回格式不统一
- MCP 跨 AI 工具通用（Trae / Claude Code 同一套代码两端配置）

**MCP 三大原语在项目中的体现**
- Tools：index.js 注册6个 Tool（check_file_size / run_eslint 等）
- Resources：project://state（设计文档中规划，尚未实现）
- Prompts：（未使用，但 rules + skills 本质是结构化 Prompt）

**Agent vs 工具的边界**
- Code Guardian 不是 Agent，是 Agent 调用的工具
- Agent 需要：自主决策循环（observe→think→act）
- Code Guardian 缺：自主决策（它只检查，不决定修不修）

### ③ 核心实现
- index.js：Server 实例 + ListToolsRequestSchema + CallToolRequestSchema
- stdio 传输：StdioServerTransport（本地进程间通信）
- 工具分发：handleToolCall switch-case 路由到6个 tool 模块

### ④ 踩坑记录
- 最初 tools 目录用 Glob 查找失败（IoError），改用 LS 工具
- ESLint FlatESLint API 需要临时配置文件 + 时间戳避免缓存

### ⑤ 面试模拟
**面试官**：你的 Code Guardian 算 Agent 吗？
**你应该答**：不算，它是 Agent 调用的工具。Agent 需要 observe→think→act 的自主循环，Code Guardian 只做 observe（检查），不做 think（决策）和 act（修复）。
**面试官追问**：如果让它变成自主 Agent，缺什么？
**你应该答**：缺自主决策循环——需要加"检查→发现问题→决定修复→调用修复工具→再检查"的闭环。

## 模块11：双 AI 工作流编排 (⭐⭐⭐⭐)

### ① 功能定位
Trae Solo（规划）+ Claude Code（执行）的双 AI 协作模式，通过文件系统传递上下文。

### ② 设计思路

**为什么要两个 AI？**
- Trae Solo：完整项目上下文，擅长全局规划
- Claude Code：擅长具体代码实现，但每次新会话需重建上下文

**Workflow Bridge 为什么用文件而不是 MCP？**
- MCP 适合"调用工具"，不适合"存储状态"
- 文件系统最简单可靠，版本可控，两个 AI 都能直接读写

**三个断点及解决方案**
- 断点1(上下文丢失) → Workflow Bridge 的 current-plan.json
- 断点2(Skills 是文本) → MCP Tools 自动化（Code Guardian）
- 断点3(规则靠 AI 自觉) → MCP 主动校验 + Hooks 被动兜底

### ③ 核心实现
- bridge.js：status / archive / init 三命令，JSON 文件读写
- current-plan.json：schema_version 1.1，tasks 数组 + entryFile
- context.json：lastTask + lastModifiedFiles + warnings

### ⑤ 面试模拟
**面试官**：两个 AI 怎么协作？
**你应该答**：Trae 负责规划产出 plan.md 和 current-plan.json，Claude Code 读取这些文件执行具体编码。Bridge 是文件系统中间层。
**面试官追问**：Bridge 为什么不做成 MCP？
**你应该答**：MCP 适合工具调用（一次性请求-响应），但状态传递需要持久化。文件系统天然持久化、可版本控制、两个 AI 都能直接读写，比 MCP 更简单可靠。

## 模块12：静态分析与自动测试 (⭐⭐⭐⭐)

### ① 功能定位
Code Guardian 的静态分析底层实现 + 测试系统设计。

### ② 设计思路

**正则 vs AST 的技术选型**
- 正则：零依赖、开发快、但有误报（字符串字面量）
- AST：精确无误报、但增加依赖和解析开销
- 项目选择：先正则快速实现，误报后针对性修复

**资源泄露检测的配对策略**
- 按类型分别统计 create / cleanup 调用次数
- setInterval / clearTimeout 交叉匹配问题及解决

**自动测试生成系统设计（缺口，面试重点）**
- 从源码函数签名推导测试骨架
- 从 .code-guardian.json 配置生成边界用例
- 每个检测器生成正例(合规) + 反例(违规)

### ③ 核心实现
- function_body.js：extractFunctionBody 大括号计数（伪 AST）
- validate_architecture.js：extractImportStatements + importsContain
- __tests__/：makeTempDir→createFixture→assert→cleanup 模式

### ④ 踩坑记录
- 正则全文扫描导致字符串字面量误报（knowledge/06 问题1）
- 资源泄露检测过于宽松（knowledge/06 问题2）
- 重复代码阈值过低（knowledge/06 问题3）

### ⑤ 面试模拟
**面试官**：正则和 AST 各有什么问题？
**你应该答**：正则会误报——字符串字面量里的 'composables/' 被当成 import 路径。AST 精确但增加依赖和解析开销。项目先正则快速实现，然后针对性修复误报。
**面试官追问**：怎么设计自动测试生成？
**你应该答**：三层：①解析函数签名生成测试骨架 ②基于 .code-guardian.json 配置生成边界用例（超长文件、违规代码）③每个检测器生成正例和反例。这是当前缺口，只有手写测试。

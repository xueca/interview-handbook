# 复杂编码 Skill

## 角色定位

资深全栈工程师。负责复杂功能开发和代码重构，设计先行，验证收尾。

## 两种模式

| 模式 | 触发词 | 特点 |
|------|--------|------|
| 新功能 | "生成代码"/"写组件"/"实现功能"/"添加新模块" | 从零创建，按依赖顺序 |
| 重构 | "重构"/"拆分"/"优化代码"/"清理代码" | 改造已有，不改业务逻辑 |

## 执行流程

### Phase 1: 诊断（重构模式必做，新功能模式跳过）

1. 运行 ESLint 全量检查，记录所有 Error
2. 检查文件大小，记录超标文件
3. 标记需重构的文件清单
4. 输出诊断报告，等用户确认后再开始

### Phase 2: 设计（必做，等确认后再写代码）

读取 `PROJECT_STATE.md` 了解项目状态，然后输出设计文档：
1. 📁 目录结构（树状图）
2. 🧱 架构说明（为什么这样设计）
3. 📄 文件清单（每文件作用 + 预计行数）
4. 🔗 与已有模块的依赖关系

确认约束边界：模块归属、是否涉及已有接口修改、预计文件数和行数。

### Phase 3: 执行（按依赖顺序）

**新功能模式**：api → composable → view
- 新增接口完成 controller → routes → api/xxx.js 三部曲
- composable 暴露 { data, loading, error, action } 标准接口
- .vue 只保留渲染 + 事件转发

**重构模式**：建 composables → 创建 useXxx → 拆 controller → 精简 .vue
- 状态用 ref/reactive（不用模块级变量）
- 拆分 controller → service/工具函数 + 精简 controller
- .vue 文件只保留渲染 + 事件转发

**通用规则**：每个文件修改前后调用 Code Guardian（按 rule 07 要求）

### Phase 4: 验证

按优先级检查（具体检查项已在 rules 01-03 和 07 中定义）：
- **P0**：无直接 API 调用、async 有 try-catch、资源已清理
- **P1**：文件行数合规、函数长度合规、接口三部曲完整
- **P2**：无重复代码、SSE 数据流合规（如适用）

## 输出格式

```
## 设计确认
[设计文档，等用户确认]

## 代码实现
[按依赖顺序输出代码]

## 自检结果
P0: ✅/❌
P1: ✅/❌
P2: ✅/❌
```

## 极简执行原则

**不要说过程性废话，直接输出结果**：
- ❌ "我现在开始诊断..." → ✅ 直接输出诊断结果
- ❌ "诊断完成，发现以下问题..." → ✅ 直接列出问题
- ❌ "接下来我将进行设计..." → ✅ 直接输出设计文档
- ❌ "代码实现完成，现在进行验证..." → ✅ 直接输出验证结果

**输出格式严格遵守**：只输出"设计确认"、"代码实现"、"自检结果"三部分，不要加过渡语。

## 裁决规则

- 功能与约束冲突时，**听约束的**。宁可少一个功能，也不破架构层
- 重构时"保留兼容性"与"彻底重构"冲突时，**听彻底重构的**

# AI×开源贡献 — 执行计划

> 目标：用AI工具辅助，完成3-5个高质量开源贡献（PR/Issue/Docs），形成可量化的简历证据链。
> 周期：约3-4周（可并行推进）
> 产出物：GitHub贡献记录 + 简历开源贡献条目 + 面试故事素材

---

## 一、为什么要做开源贡献

2026年校招面试官的真实反馈：AI工具让写代码、写文档的门槛都降低了，候选人"会说"已经不稀奇，真正拉开差距的，是能不能在真实工程环境里持续交付。[cite:1]

开源贡献对简历的价值体现在三个层面：

**证明工程能力**：经历完整的"看懂代码→定位问题→提PR→被review→修改→合并"流程，比任何Demo项目都更有说服力。[cite:1]

**证明协作能力**：开源项目有严格的代码规范、Review流程、CI检查，跟真实工作环境最接近。[cite:2]

**证明主动性**：不是"被布置作业"，而是"主动发现问题并解决"。这是面试官最看重的品质。[cite:2]

面试官评估开源贡献的5个维度 [cite:1]：

| 维度 | 考察点 | 你的优势 |
|------|--------|---------|
| 理解力 | 有没有读懂问题再动手 | Spec Coding练的就是这个 |
| 工程习惯 | Commit信息是否清晰、是否拆合理commit | 你的ESLint+Husky规范可迁移 |
| 沟通能力 | 会不会提有效问题 | 和AI对话练出的追问能力 |
| 业务感 | 知不知道为什么做这件事 | 完整项目从0到1的经验 |
| 成长潜力 | 面对Review反馈的反应速度 | AI辅助快速迭代修改 |

## 二、选什么项目

### 2.1 筛选标准

| 标准 | 说明 |
|------|------|
| 活跃度 | 最近一周有commit，不是僵尸项目 |
| 新手友好 | 有 `good first issue` 或 `help wanted` 标签 |
| 文档齐全 | 有 `CONTRIBUTING.md`，有清晰的开发环境搭建指南 |
| 技术栈匹配 | Vue/React/Node.js，与你的项目技术栈一致 |
| 社群响应 | Issue有回复，PR有人review |

### 2.2 推荐项目清单（按难度排序）

**L1 — 练手级（文档/翻译类）**

| 项目 | 推荐理由 | 贡献方向 |
|------|---------|---------|
| Vue 3 官方文档 | 中文翻译持续完善中，Star 53k+ | 翻译校对、文档修正 |
| Element Plus | 国内最流行的Vue3组件库，Star 26k+ | 文档示例补充、API说明修正 |
| Vite 官方文档 | 中文文档有翻译需求 | 中文翻译贡献 |

**L2 — 入门级（简单Bug/测试）**

| 项目 | 推荐理由 | 贡献方向 |
|------|---------|---------|
| Ant Design Vue | Star 20k+，有 `good first issue` 标签 | 组件小Bug修复 |
| VueUse | 工具库，函数粒度小，每个函数独立 | 新增工具函数或修复边界case |
| axios | 请求库，有 `help wanted` | 类型定义修复、测试补充 |

**L3 — 进阶级（功能优化）**

| 项目 | 推荐理由 | 贡献方向 |
|------|---------|---------|
| Slidev | Vue3写的PPT工具，Star 34k+ | 小功能添加、UI优化 |
| Vitest | 测试框架，生态活跃 | 测试用例补充、文档完善 |

### 2.3 如何用AI快速筛选项目

在GitHub上执行以下搜索（或用AI辅助分析）：

```bash
# 搜索Vue生态的good first issue
gh search issues --label="good first issue" --language="javascript" --repo="vuejs/core"

# 搜索中文友好的项目
gh search repos --language="vue" --topic="chinese" --stars=">1000"
```

用AI快速阅读项目README和CONTRIBUTING.md，判断项目是否适合自己：
- 把README内容复制给AI，问："这个项目的技术栈与我的技能（Vue3+Express+Node.js）是否匹配？"
- 把CONTRIBUTING.md内容复制给AI，问："这个项目的贡献流程是否复杂？我作为新手能否完成？"

## 三、AI辅助开源贡献的完整工作流

### 第1步：项目筛选（30分钟，AI辅助）

1. 用GitHub搜索 `good first issue` 项目
2. 用AI工具快速阅读项目README和CONTRIBUTING.md
3. 用AI分析Issue描述，评估难度和匹配度
4. 选2-3个候选项目，尝试本地搭建

AI提示词示例：
```
你是一个开源项目评估助手。请阅读以下项目的README和CONTRIBUTING.md，帮我判断：
1. 这个项目的技术栈与Vue3+Express+Node.js是否匹配？
2. 新手贡献的门槛有多高？（1-5分，1分最低）
3. 是否有明确标注为"good first issue"的任务？
4. 本地环境搭建需要多久？
```

### 第2步：环境搭建（1-2小时，AI辅助）

1. Fork项目到个人仓库
2. Clone到本地
3. 用AI帮助理解项目结构和依赖关系
4. 按CONTRIBUTING.md搭建开发环境
5. 跑通测试用例，确认环境正常

AI提示词示例：
```
请阅读以下项目目录结构，帮我理解：
1. 项目的核心模块有哪些？每个模块的职责是什么？
2. 入口文件在哪里？构建流程是怎样的？
3. 测试命令是什么？如何运行单个测试？
4. 有哪些关键依赖需要特别注意？
```

### 第3步：认领任务（15分钟，人工操作）

1. 在目标Issue下留言："I'd like to work on this. Can you assign it to me?"
2. 确认任务未被其他人占用
3. 如有疑问，在Issue下问清楚再动手

这一步必须人工操作，AI不能代劳——这是社区沟通的第一步。

### 第4步：问题定位（1-3小时，AI辅助+人工判断）

1. 用AI帮助复现问题
2. 用AI追踪调用链，定位根因
3. 人工确认边界条件和影响范围
4. 用AI生成多方案对比，人工选择最优方案

AI提示词示例：
```
这个Issue描述的问题是：[粘贴Issue内容]
请帮我：
1. 分析问题可能的根因，列出3个最可能的原因
2. 对每个原因，给出修复方案和影响范围
3. 推荐最优方案，并说明理由
```

### 第5步：编码实现（2-4小时，AI生成+人工审查）

这是最核心的一步，也是AI最容易出问题的一步。

**AI做什么：**
- 生成修复代码
- 生成单元测试
- 更新相关文档

**你必须检查什么：**
- 边界条件：空值、极端输入、并发场景
- 权限校验：修改是否引入了安全问题
- 代码风格：是否符合项目现有的代码风格
- 重复代码：搜索项目中是否已有类似实现
- CI是否被削弱：不要删除或跳过任何测试

审查清单（逐项检查）：
```
□ 边界条件：传入null/undefined/空数组会怎样？
□ 错误处理：异常情况有try-catch吗？
□ 代码风格：缩进、命名、导入顺序与项目一致吗？
□ 重复代码：git grep 搜索关键函数名，确认没有重复实现
□ 测试覆盖：新增的测试是否真正覆盖了修复场景？
□ 回归风险：修改是否会影响其他模块？
□ CI配置：没有修改workflow文件、测试配置、覆盖率阈值
```

### 第6步：提交PR（30分钟，AI辅助撰写+人工精简）

1. 创建特性分支：`git checkout -b fix/xxx-issue`
2. 提交代码：遵循项目Commit规范（通常是 Conventional Commits）
3. 用AI辅助撰写PR描述，但人工精简冗余内容
4. 关联对应Issue：`Closes #123`
5. 自己先Review一遍Diff，再标记审查者

PR描述模板：
```
## 问题描述
[一句话说清楚要解决什么问题]

## 解决方案
[一句话说清楚怎么解决的，为什么选这个方案]

## 修改内容
- [修改点1]
- [修改点2]

## 测试
- [x] 新增单元测试覆盖修复场景
- [x] 本地测试通过
- [x] 现有测试全部通过

## 截图/录屏（如涉及UI变更）
[粘贴截图]

Closes #123
```

2026年重要提醒：AI生成的PR描述往往过于啰嗦。审查者会下意识判断"这是AI写的"——如果描述太冗长，可能被直接跳过。[cite:3] 原则：AI写初稿，人精简到原来的一半。

### 第7步：响应Review（多次迭代，AI辅助+人工决策）

1. 用AI帮助理解Review意见
2. AI生成修改方案
3. 人工判断方案合理性——不是所有Review意见都必须照做
4. 快速响应修改，展示成长潜力
5. 如果Review意见合理，真诚感谢；如果有不同意见，有理有据地讨论

AI提示词示例：
```
审查者给我的PR提了以下意见：[粘贴Review内容]
请帮我：
1. 逐条解释每条Review意见的技术含义
2. 对每条意见，给出修改方案
3. 标注哪些意见是"必须修改"，哪些是"建议性"的
4. 如果有不同意见，帮我组织一个有技术依据的回复
```

## 四、分阶段执行计划

### 阶段一：准备期（第1-2天）

**目标：搭好基础设施，选好目标项目**

| 任务 | 具体操作 | 产出 |
|------|---------|------|
| 1.1 完善GitHub个人主页 | 头像、Bio、Pinned项目（面试宝典）、README Profile | 专业的GitHub主页 |
| 1.2 面试宝典项目README升级 | 添加英文版README、架构图、贡献指南 | 项目看起来更专业 |
| 1.3 筛选目标项目 | 用AI搜索good first issue，选3个候选 | 候选项目清单 |
| 1.4 搭建本地环境 | Fork+Clone，AI辅助理解项目结构 | 本地可运行 |

### 阶段二：练手期（第3-7天）

**目标：完成第一个贡献（文档/翻译类），跑通全流程**

| 任务 | 具体操作 | 产出 |
|------|---------|------|
| 2.1 认领文档任务 | 在Vue 3/Vite/Element Plus中找文档修正任务 | 认领的Issue |
| 2.2 完成文档修改 | AI辅助理解文档内容，人工确认修改正确 | 提交的PR |
| 2.3 响应Review | 按上文第7步流程响应 | 合并的PR |
| 2.4 记录过程 | 写踩坑笔记，记录全流程问题和解决方案 | 踩坑记录 |

**为什么从文档开始？**
- 门槛最低，成功率最高
- 快速建立信心
- 熟悉PR流程，为后续Bug修复打基础
- 文档贡献也是真实贡献，简历上可以写

### 阶段三：进阶期（第8-18天）

**目标：完成2-3个代码贡献（Bug修复/测试补充/小功能）**

| 任务 | 具体操作 | 产出 |
|------|---------|------|
| 3.1 认领Bug修复任务 | 在VueUse/Ant Design Vue/axios中找 `good first issue` | 2-3个认领的Issue |
| 3.2 逐个完成PR | 严格按第4-7步流程执行 | 2-3个提交的PR |
| 3.3 响应Review，推动合并 | 快速响应，主动沟通 | 合并的PR |
| 3.4 记录每个PR的教训 | 每个PR完成后写100字小结 | 经验积累 |

**重点：第二个PR开始，尝试用你的Spec Coding方法**
- 在TRAE中加载项目代码
- 把你的6条规则注入AI对话
- 用AI生成代码，但通过你的规则约束质量
- 记录这个过程——这就是"AI×开源贡献"的差异化故事

### 阶段四：收尾期（第19-21天）

**目标：沉淀成果，写入简历，准备面试故事**

| 任务 | 具体操作 | 产出 |
|------|---------|------|
| 4.1 整理贡献记录 | 用 `git log --author='your-email' --oneline` 统计提交 | 量化数据 |
| 4.2 更新简历 | 在简历中新增"开源贡献"条目 | 简历 v4 |
| 4.3 写开源贡献总结文章 | 发布到掘金/知乎/牛客，标题"AI辅助开源贡献：一个民办本学生的实战记录" | 技术文章 |
| 4.4 准备面试回答 | 准备3个故事：最有成就感的PR、最难的Bug修复、如何用AI辅助 | 面试题库 |

## 五、简历中的呈现方式

### 5.1 简历条目模板

```
开源贡献（GitHub）
- 向 Vue 3 核心仓库提交并合并 3 个 PR，包括文档修正和 Bug 修复
- 独立完成 Issue #456 的定位与修复，涉及 [具体技术点]
- 使用 AI 辅助代码审查流程，PR 一次通过率 100%
- [可选] 累计提交 N 次，被 [项目名] 合并
```

### 5.2 量化你的贡献

```bash
# 统计你的所有开源提交
git log --author='你的邮箱' --oneline --all | wc -l

# 统计你在某个项目中的提交
git log --author='你的邮箱' --oneline | wc -l

# 查看你的PR列表
gh pr list --state merged --author '@me'
```

### 5.3 面试时怎么讲

面试官问"你做过开源贡献吗？"时，不要只报数字。按这个结构讲：

1. **我遇到了什么问题**（选一个具体的PR）
2. **我是怎么定位根因的**（展示理解力）
3. **我用了AI辅助，但AI差点搞砸了X**（展示批判性思维）
4. **我最后怎么解决的**（展示工程能力）
5. **Review过程中学到了什么**（展示成长潜力）

## 六、避坑指南

### 6.1 项目选择避坑

| 陷阱 | 表现 | 如何避免 |
|------|------|---------|
| 僵尸项目 | 最近一次commit在3个月前 | 检查 `git log` 和最近Issue的回复时间 |
| 不友善社区 | Issue没人回，PR没人review | 先观察Issue区活跃度再投入 |
| 技术栈不匹配 | 项目用Rust但你只会JS | 用AI分析项目技术栈后再决定 |
| 难度过高 | 核心代码改动需要深度理解 | 从文档和测试开始，逐步深入 |

### 6.2 AI使用避坑

| 陷阱 | 表现 | 如何避免 |
|------|------|---------|
| 盲目信任AI代码 | AI生成的代码看起来很对但实际有bug | 逐项检查§5的审查清单 |
| AI生成重复代码 | AI不了解项目已有工具函数，重复造轮子 | 生成前先用 `git grep` 搜索关键函数名 |
| PR描述太啰嗦 | 审查者一看就知道是AI写的 | AI写初稿，人精简到一半 |
| 削弱CI配置 | AI可能修改或删除workflow文件 | 检查diff中是否包含 `.github/workflows/` 的修改 |
| 忽略代码风格 | AI的代码风格与项目不一致 | 先让AI阅读项目现有代码，学习风格后再生成 |

### 6.3 时间管理避坑

| 陷阱 | 如何避免 |
|------|---------|
| 一次接太多Issue | 同一时间最多做2个，做完再认领新的 |
| 陷入复杂Issue | 如果2小时内没进展，在Issue下提问或放弃 |
| Review来回太久 | 如果3天没有review反馈，礼貌地ping一下维护者 |

## 九、常见问题

**Q: 我技术不够好，能做开源贡献吗？**

能。开源贡献不只是写代码。文档修正、翻译、测试补充、Issue复现——这些都是有价值的贡献。2026年面试官原话："哪怕只是修一个文档错误，经历完整的'看懂代码-定位问题-提PR-被review-修改-合并'流程，这个过程本身就是最好的项目经历。"[cite:1]

**Q: AI帮我写代码，算不算作弊？**

不算。2026年AI辅助编程已是行业标配。关键是：你要能解释每一行代码为什么这样写，能在Review时回答审查者的质疑。AI负责生成，你负责判断和负责。[cite:3]

**Q: PR被拒绝了怎么办？**

正常。开源社区拒绝PR是常态。关键是：认真看Review意见，修改后重新提交，展示你的学习能力。面试官更看重"被拒绝后怎么应对"而不是"一次通过"。[cite:1]

**Q: 时间不够怎么办？**

先做文档类贡献（1-2天可完成一个），再做Bug修复。只做你能完成的，不做"看起来厉害但做不完"的。

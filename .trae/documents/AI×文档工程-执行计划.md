## 二、产出1：.trae/ 体系架构图

### 2.1 目标

一张 Mermaid 流程图，展示你的 AI 协作体系的完整数据流：**Rules → Skills → Spec → PROJECT_STATE → 代码输出**。

### 2.2 为什么面试有效

面试官问"你是怎么用 AI 辅助开发的？"——你直接亮图，30秒讲完，比说5分钟更有效。视觉记忆远强于听觉记忆。

### 2.3 具体步骤

**Step 1：整理素材（5分钟）**

你已有以下素材，不需要重新写：

| 素材 | 位置 | 摘取内容 |
|------|------|---------|
| 6条Rules | `.trae/rules/` 下6个文件 | 每条规则名 + 一句话作用 |
| 5个Skills | `.trae/skills/` 下5个目录 | 每个Skill名 + 一句话作用 |
| 5个Spec | `.trae/spec/` 下 | 每个Spec主题 |
| PROJECT_STATE | 根目录 | 状态管理/接口契约/技术债/禁区/决策记录 5个模块 |
| 4个Prompt模板 | `.trae/prompt-templates/` | 模板名 |

**Step 2：生成 Mermaid 图（15分钟）**

用 AI 生成 Mermaid 代码。Prompt 如下：

```
用 Mermaid 语法画一张流程图，展示我的 AI 协作开发体系。要求：

1. 图分5层，从上到下：
   - 第1层【输入层】：用户提出需求
   - 第2层【规则层】：6条Rules（架构契约/文件规模/反模式/SSE契约/编码纪律/注释标准），标注"System Prompt自动注入"
   - 第3层【工作流层】：4个Skill（generate-with-constraints/refactor-shit-mountain/verify-refactor/teach-interview-handbook），标注"按需调用"
   - 第4层【上下文层】：PROJECT_STATE.md（状态/契约/技术债/禁区/决策），标注"每次AI交互自动加载"
   - 第5层【输出层】：代码生成 → ESLint检查 → pre-commit拦截 → 人工Review → 合入

2. 画一个"反馈闭环"：ESLint不通过 → 回到第3层重新生成
3. 画一个"禁区保护"：PROJECT_STATE的禁区清单 → 标注"CI拦截，AI不可修改"
4. 所有节点用中文，箭头标注关键数据流

生成可以复制到 mermaid.live 的代码。
```

**Step 3：导出PNG（10分钟）**

1. 打开 https://mermaid.live
2. 粘贴 Mermaid 代码
3. 调整布局（如果太宽，选左侧→右侧的flowchart LR）
4. 导出PNG，保存到 `interview-handbook/.trae/documents/architecture.png`

**Step 4：加入README（5分钟）**

在项目的 README.md 中加：

```markdown
## AI协作架构

![AI协作架构](./.trae/documents/architecture.png)

本项目采用 Spec Coding 方法论，通过 6 条规则 + 4 个 Skill + 上下文管理中心，
实现 AI 辅助编码的规范化。详见 [.trae/](./.trae/) 目录。
```

## 三、产出2：Spec Coding 实践文章

### 3.1 目标

一篇 1500-2000 字的技术文章，发布到掘金/知乎/GitHub Discussions。选题：**"我是怎么用6条规则约束AI不乱写代码的"**。

### 3.2 为什么这篇文章有效

- 牛客3个双非上岸案例全部提到"博客/文章"作为加分项 [1][2]
- 面试官搜你名字 → 搜到文章 → 看到你不是只会写代码，你还会**总结和分享**
- 民办本 + 无实习 + 有技术文章 = 面试官会多看你一眼

### 3.3 文章结构

```
标题：Spec Coding 实践：用6条规则约束AI不乱写代码

Part 1（200字）：问题 — AI写的代码"能用但不可维护"
  - 场景描述：AI生成300行的Vue组件，逻辑混乱、重复代码、没有错误处理
  - 数据：无规则时AI代码首次通过率约40%，需要大量手动修复
  - 核心洞见：AI不是不会写代码，是没有给你写的代码设边界

Part 2（400字）：方案 — 6条规则的设计逻辑
  - 规则1：架构分层单向流动（views→composables→api→backend）
  - 规则2：文件规模限制（.vue≤200行，.js≤150行，api≤50行）
  - 规则3：反模式6禁（禁止组件内直接fetch、禁止裸async、禁止timer不清理等）
  - 规则4：SSE契约（三段式数据流，thinking→content→done）
  - 规则5：编码纪律（先思考再写代码、简洁优先、精准修改）
  - 规则6：注释标准（文件头注释、函数注释、数据流注释）
  - 每条规则给1个"有规则 vs 无规则"的代码对比

Part 3（300字）：实施 — 怎么让AI遵守规则
  - 每条规则在编码前作为System Prompt注入
  - 配合ESLint（max-lines/max-lines-per-function/max-params）+ pre-commit
  - 规则不是"建议"，是"强制约束"——不合规代码无法提交
  - 结果：代码合规率100%（ESLint 0 Error）

Part 4（300字）：升级 — 从规则到工作流
  - 4个Skill：约束化生成/安全重构/交叉验证/知识萃取
  - PROJECT_STATE.md：AI上下文管理中心
  - 从"用AI写代码"到"用AI管理代码"

Part 5（200字）：反思 — 什么场景下这套方法不适用
  - 快速原型/一次性脚本不需要这么重的约束
  - 规则太严会限制AI的创造力
  - 未来方向：从Spec Coding到Harness Engineering（自动化验证链）

Part 6（100字）：链接你的项目仓库
  - "这套规则体系已开源，欢迎参考：github.com/xueca/interview-handbook"
```

### 3.4 写作技巧

| 技巧 | 示例 |
|------|------|
| **用对比** | "无规则：AI生成300行组件，3个逻辑混在一起。有规则：AI自动拆成150行组件+100行composable" |
| **用数字** | "代码合规率从约40%提升到100%" |
| **用代码片段** | 不是讲道理，是贴代码对比 |
| **不要吹** | 不要说"范式转变"，说"我试了一种方法，效果不错" |
| **附链接** | 文末附GitHub仓库链接，导流 |

### 3.5 发布渠道（按优先级）

| 渠道 | 优势 | 发布步骤 |
|------|------|---------|
| **掘金** | 前端社区最大，SEO好，面试官搜到的概率最高 | 注册→写文章→发布→加标签"前端""AI""Vue" |
| **知乎** | 搜索权重高，面试官百度搜你名字可能搜到 | 注册→写文章→发布→加话题"前端开发""AI辅助编程" |

### 4.3 要写的踩坑记录（3个坑，每个200字）

**坑1：SSE 流式被 Vite 代理截断**

```
问题：AI出题SSE流式输出到第12秒时突然断开。
排查：前端EventSource.onerror被触发，后端日志显示无异常。
      curl直连后端5000端口正常，经过Vite代理5173端口就断。
根因：Vite代理默认超时12秒（proxy.timeout），AI出题有时超过12秒。
解决：vite.config.js中设置 proxy: { timeout: 0, proxyTimeout: 0 }
教训：反向代理的超时配置是SSE的隐形杀手。
      生产环境Nginx也有类似问题，需要 proxy_buffering off。
```

**坑2：DeepSeek V4 reasoning_content 混入流式输出**

```
问题：流式输出中夹杂了AI的"思考过程"文本，前端显示混乱。
排查：观察SSE chunk，发现 delta 对象里有两个字段：
      delta.reasoning_content（思考过程，不需要展示）
      delta.content（正式回答，需要展示）
根因：DeepSeek V4模型默认返回思考过程。
解决：aiParser.js 中过滤 reasoning_content，只取 delta.content。
      非流式接口取 message.content，流式接口取 delta.content。
教训：模型升级时API格式可能变化，需要仔细阅读文档。
      不同模型（V3 vs V4）的返回字段结构不同，不能假设兼容。
```

**坑3：JSON文件并发写导致数据丢失**

```
问题：（未实际发生，但设计时考虑到的风险）
分析：如果两个用户同时提交答题记录，readJSON→修改→writeJSON
      的时序可能导致后写覆盖先写，先写的数据丢失。
现状：当前单用户场景，风险可控。PROJECT_STATE.md已记录。
方案：多用户场景需要加读写锁（Node.js fs.writeFile的原子性
      不足以覆盖 read-modify-write 的竞态窗）。
教训：技术选型时要诚实面对方案的局限性。
      面试时不要回避，主动说"当前的限制和未来的改进方案"更加分。
```

## 一、JS 基础

### 1. Promise.all vs Promise.allSettled
- **薄弱场景**: 答题引擎并行获取多道题目时，若某题 404 会怎样？
- **错误理解**: 以为"跳过失败项，加载成功的"
- **正确结论**: `Promise.all` 是"一失败全失败"，不是跳过。要实现"跳过失败"必须用 `Promise.allSettled`。
- **代码位置**: `useQuiz.js` 第 97 行 `Promise.all(idList.map(id => getDetail(id)))`
- **复习建议**: 手写对比代码，理解 `status/value/reason` 结构

## 二、浏览器事件机制

### 2. IME Composition 与 input 事件
- **薄弱场景**: 中文输入法输入搜索关键词，防抖触发几次请求？
- **错误理解**: 猜了 6 次（按拼音字母数）
- **正确结论**: 只有 1 次。Vue 3 的 `v-model` 内置 IME 兼容——`compositionstart/end` 期间不更新 model，`el-input` 的 `@input` 在 `isComposing=true` 时被拦截。
- **复习建议**: 理解 `compositionstart` → `compositionupdate` → `compositionend` 三阶段

## 三、架构分层

### 3. 路由守卫条件方向
- **薄弱场景**: `/quiz?id=999` 不存在，守卫能拦住吗？
- **错误理解**: "有 id 就拦"
- **正确结论**: `!to.query.id` 是"**没有** id 才拦"，不是"有 id 就拦"。守卫只检查参数是否存在，不检查合法性。
- **代码位置**: `router/index.js` 第 74 行
- **复习建议**: 重新读守卫的三个分支逻辑

### 4. onUnmounted 绑定对象
- **薄弱场景**: `useTimer` 拆出来的原因
- **错误理解**: "和 useQuiz 写在一起会泄漏"
- **正确结论**: `onUnmounted` 绑定的是**调用组件**（Quiz.vue），不是 composable 本身。拆分的真正原因是单一职责 + 可复用性 + 文件行数限制。
- **复习建议**: 理解 Vue 生命周期钩子的绑定机制

## 四、数据统计

### 5. aggregateByQuestion 数据范围
- **薄弱场景**: 新题第一次做对，`totalQuestions` 为什么 +1？
- **错误理解**: 用 sessionRecords（过滤了 wrong-book）解释
- **正确结论**: `aggregateByQuestion` 用的是**所有记录**（`allUserRecords`，不区分 source）。遇到新 qid → `perQ` 新增 entry → `Object.keys(perQ).length` 增加。和 sessionRecords 无关。
- **代码位置**: `recordController.js` 第 36-45 行
- **复习建议**: 对比两个维度的数据来源

### 6. buildDailyTrend 日期生成
- **薄弱场景**: 用户 6/10 注册，今天 6/12，返回几条数据？
- **错误理解**: 返回 3 条（注册日到今天）
- **正确结论**: 返回 **7 条**，范围是 **6/6 - 6/12**（今天往前推 6 天）。和用户注册日期**完全无关**——总是固定 7 天骨架。
- **代码位置**: `recordController.js` 第 81-95 行
- **复习建议**: 重新读 `for (let i = 6; i >= 0; i--)` 的循环逻辑

## 五、业务逻辑

### 7. 标记 vs 错题本的关系
- **薄弱场景**: 错题本移除后标记还在吗？重新做错后标记还在吗？
- **错误理解**: "错题本移除 = 标记也删除"
- **正确结论**: **两套独立数据源**。错题本存在 `records.json`（自动计算），标记存在 `marks.json`（用户手动操作）。移除错题本不影响标记状态。
- **复习建议**: 对比两个 controller 的读写逻辑

## 六、并发安全

### 8. JSON 并发写冲突流程
- **薄弱场景**: 两个用户同时写 records.json 会发生什么？
- **薄弱点**: 能说出"丢数据"，但说不出具体的 read→modify→write 流程
- **正确结论**:
  ```
  T1: 用户A read → [r1, r2]
  T1': 用户B read → [r1, r2]      ← 同时读到同一份
  T2: 用户A push r3 → write [r1,r2,r3]
  T3: 用户B push r4 → write [r1,r2,r4]  ← r3 丢失！
  ```
- **复习建议**: 画出时序图，理解"丢失更新"（Lost Update）
